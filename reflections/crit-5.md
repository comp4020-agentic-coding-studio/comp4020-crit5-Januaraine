# Crit 5 

**What was the breakthrough that moved the work forward?**

The biggest breakthrough was realising that the game should be designed around consistent rules rather than individual visual fixes. Initially, when the DVD logo behaved incorrectly, I tended to think about the problem as a local bug: the logo was too slow, the trajectory was too horizontal, or the corner detection was too difficult. The turning point was when I changed the paddle collision to use an angle-based reflection model. Instead of manually adjusting the velocity after each collision, the game now derives the new direction from the collision position while preserving the overall speed within reasonable limits. This gave me a much more stable foundation for later features. Once the movement was reliable, I could build game modes, scoring, speed effects and difficulty levels around it without constantly breaking the underlying gameplay. I also learned that testing the game myself revealed problems that were difficult to predict from the implementation alone. For example, the fullscreen resize problem only became obvious when I changed the browser window during play. These experiences showed me that the important breakthroughs were not always new features; sometimes they were changes in the underlying model that made the rest of the project easier to develop.


**What did this work change about who I want to be as a software developer?**

This project changed my view of software development from simply implementing requested features to iteratively designing and validating an interactive system. I learned that a feature can be technically correct but still produce a poor user experience. For example, my corner detection could correctly identify a collision, but if the player could rarely achieve it, the game was not enjoyable. Similarly, the original collision implementation could pass basic tests while still producing movement that felt wrong when actually playing. Working with the coding agent also changed how I approach development. Instead of asking the agent to simply "fix" a symptom, I increasingly learned to describe the desired behaviour, explain the problem I observed, and ask it to identify the underlying cause. I then tested the result and used the new behaviour to decide what should happen next. This made me more interested in becoming a developer who focuses on interaction, behaviour and system design, rather than only writing code that satisfies a specification. In future projects, I want to keep this iterative approach: build something, observe how it actually behaves, identify the underlying problem, and then improve the design rather than repeatedly patching individual symptoms.
